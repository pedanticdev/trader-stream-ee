Garbage Collection Fundamentals

TermDefinition
Young GenerationWhere new objects are allocated. Collected frequently, typically via copying collector.
Old GenerationWhere long-lived objects reside after surviving multiple young GC cycles.

Simon: Quick refresher on GC terminology. The key concepts for today are stop-the-world, remembered sets, and write barriers. These are the mechanisms that create pause problems in G1.

Remembered sets exist because generational collectors need to know which old-generation objects point to young-generation objects during young GC. Every reference update triggers a write barrier to track this.

G1GC: The Default Collector

How It Works

Design Goals

  • Target pause time (default: 200ms)
  • Heap divided into regions (~2048)
  • Generational: young + old regions
  • Concurrent marking phase
  • Mixed collections for old gen

The Catch

  • Young GC: STW, copies live objects
  • Mixed GC: STW, evacuates old regions
  • Full GC: STW, compacts entire heap
  • All collections pause the application
  • Pause time scales with live set size

G1 is an excellent general-purpose collector. It balances throughput and pause times for most applications. But for latency-sensitive financial workloads, the STW pauses are a fundamental architectural constraint.

Simon: G1 is good for most workloads. It targets 200ms pauses by default, and you can tune it down to maybe 10-20ms for modest heaps. But the pauses never go to zero, and they scale with live set size.

The target pause time is a hint, not a guarantee. Under allocation pressure, G1 will exceed it.

G1's Architectural Limitations

Why STW Is Unavoidable

Mixed Collections

  • Must trace entire live set
  • Pause scales with heap size
  • 2 GB heap: 50-100 ms
  • 4 GB heap: 100-200 ms

Remembered Sets

  • Track old-to-young refs
  • Write barrier on every pointer update
  • Scanned during every young GC
  • Overhead proportional to cross-refs

Compaction

  • Fragmentation triggers compaction
  • Full compaction requires Full GC
  • Small objects = more fragmentation
  • No concurrent compaction in G1

Key Point: These are architectural constraints, not tuning problems. No amount of JVM flag adjustment eliminates them.

Simon: You can't tune your way out of these. MaxGCPauseMillis is a hint - G1 will exceed it. Remembered sets grow with cross-generational references, and there's no concurrent compaction.

We're going to demonstrate each of these weaknesses with targeted test scenarios later in the presentation.

Azul C4 (Continuously Concurrent Compacting)

Concurrent by Design

Loaded Value Barrier (LVB)

  • Intercepts every reference load
  • Self-healing: fixes references in-place
  • Enables concurrent compaction
  • Performs NMT check + page protection check
  • Dramatically reduced trigger frequency

Simultaneous-Generational Concurrency

  • Has young and old generations
  • Both collected concurrently and simultaneously
  • No STW for generational collection
  • Filtered write barrier (SVB) for card marks
  • Interlocks for cross-generational synchronization

Result: Sub-millisecond GC pauses regardless of heap size, live set size, or allocation rate.

C4 = algorithm name · GPGC = collector name in JMX · Includes sub-ms safepoints at phase changes

Simon: This is where Azul differs fundamentally. C4 uses a read barrier - the Loaded Value Barrier. Every time your code reads a field, C4 checks if the object has been relocated. If so, it fixes up the reference in-place. The barrier is self-healing: once a reference is corrected, it stores the fix back so it won't trigger again.

C4 IS generational - it has young and old generations. But unlike G1, both are collected concurrently and simultaneously. The young collector can run multiple cycles while the old collector is in the middle of a full heap collection. This is called simultaneous-generational concurrency.

C4 still uses card marks for old-to-young references via a filtered write barrier (SVB). But there's no remembered set scanning during STW pauses, because there are no STW pauses. The card marks are scanned concurrently.

All phases run concurrently with application threads. The LVB handles object forwarding transparently. Sub-ms safepoints occur at phase change boundaries.

Simon: Compare this to the G1 timeline. With C4, the application effectively never stops. Mark, relocate, remap - all happen concurrently. The algorithm itself is fully concurrent - no global safepoints are required by the algorithm.

The current implementation does include some very short global safepoints at phase change locations for practical engineering reasons. But the work done in these safepoints is independent of heap size, and they measure in the sub-millisecond range on modern hardware. In practice, scheduling and thread contention dominate any remaining jitter.

The LVB makes concurrent compaction possible through self-healing. When the GC relocates an object, the LVB follows the forwarding pointer on first access and writes the fix back to the source location, so it won't trigger again.

Simon: This table summarizes the architectural differences. G1's STW pauses are inherent to its design - you can't tune them away. C4's pauses, by contrast, are limited to sub-millisecond safepoints at phase change boundaries, and the work done there is independent of heap size.

Note that C4 also uses remembered sets - it uses a classic card marking mechanism with a filtered write barrier (SVB). The key difference is that C4 scans card marks concurrently, while G1 must scan them during STW pauses.

Aeron IPC: Zero-Copy Transport

Bypassing the Kernel

Traditional Messaging

  • Kernel context switches
  • Buffer copies at each layer
  • Serialization/deserialization
  • Latency: 10-100+ microseconds

Aeron IPC

  • Memory-mapped shared files
  • Direct memory access
  • Zero-copy with SBE
  • No kernel involvement
  • Transport latency: sub-microsecond

Luqman: Aeron uses memory-mapped files for IPC on the same machine. The publisher writes to a ring buffer in shared memory, the subscriber reads from it. No serialization, no kernel calls, no buffer copies.

The BackoffIdleStrategy is important: it spins 100 times, yields 10 times, then parks with increasing durations. This minimizes latency when messages are arriving fast but backs off to save CPU when idle.

SBE codecs wrap existing byte buffers. They read and write directly from/to memory without creating intermediate Java objects. The buffer is reused across messages.

Luqman: SBE is the encoding protocol used by FIX Trading and major exchanges. The key insight: encoder and decoder objects are flyweights that wrap a shared UnsafeBuffer. No new objects are created during encoding or decoding.

Prices are stored as fixed-point integers (price * 10000). This avoids floating-point representation entirely in the binary format. Conversion to double happens only when building JSON for WebSocket clients.

SBE: Zero-Copy Message Processing

The Flyweight Pattern in Practice


// Reusable decoder instances - allocated once, never GC'd
private final TradeDecoder tradeDecoder = new TradeDecoder();
private final MessageHeaderDecoder headerDecoder = new MessageHeaderDecoder();
private final byte[] symbolBuffer = new byte[128];  // reused
private final StringBuilder sb = new StringBuilder(1024); // reused

@Override
public void onFragment(DirectBuffer buffer, int offset,
                       int length, Header header) {
    // Wrap existing buffer - NO copy, NO allocation
    headerDecoder.wrap(buffer, offset);

    // Move decoder window over buffer - NO allocation
    tradeDecoder.wrap(buffer,
        offset + headerDecoder.encodedLength(),
        headerDecoder.blockLength(),
        headerDecoder.version());

    // Read directly from buffer memory
    final long timestamp = tradeDecoder.timestamp();
    final long price = tradeDecoder.price();
    final int quantity = tradeDecoder.quantity();
}

Decoders are views over byte buffers. No Java objects created during message processing. The symbolBuffer and jsonBuilder are reused across calls.

Luqman: This code is from MarketDataFragmentHandler. The decoders wrap the DirectBuffer - they don't copy data. Every field access reads directly from the underlying byte array.

The symbolBuffer and jsonBuilder are instance fields, reused across millions of messages. This is the opposite of how most Java code works - normally every message processing step creates temporary objects. Here, we've eliminated allocation from the hot path entirely.

The Publisher: Burst Pattern

Simulating Realistic Market Conditions


// Burst: 500 iterations x (Trade + Quote + MarketDepth) = 1,500 messages
// Then 5-microsecond park, repeat
while (running) {
    int burstMultiplier = getBurstMultiplier(); // time-based
    int adjustedBurstSize = BASE_BURST_SIZE * burstMultiplier; // 500, 2500, or 1500

    for (int i = 0; i < adjustedBurstSize; i++) {
        publishTrade();       // SBE encode -> Aeron offer
        publishQuote();       // SBE encode -> Aeron offer
        publishMarketDepth(); // SBE encode -> Aeron offer
        if (i % 100 == 0) publishHeartbeat();
    }
    LockSupport.parkNanos(5_000); // 5us backoff between bursts
}

// Burst multiplier based on time-of-minute simulation
private int getBurstMultiplier() {
    long second = (System.currentTimeMillis() / 1000) % 60;
    if (second >= 20 && second < 25) return 5;  // News event
    if (second >= 45 && second < 50) return 3;  // Market close
    return 1; // Normal trading
}

Luqman: The publisher runs on a virtual thread and generates 1,500 messages per burst cycle. The time-based multiplier creates realistic market conditions: normal trading, then a 5x news event spike, then a 3x market close rush.

This pattern creates predictable allocation spikes that expose how different GCs handle variable load.

Virtual Threads via Jakarta Concurrency 3.1

Massive Concurrency Without Platform Thread Pools


// Single annotation defines a virtual thread executor
@ApplicationScoped
@ManagedExecutorDefinition(
    name = "java:module/concurrent/VirtualThreadExecutor",
    virtual = true,
    qualifiers = {VirtualThreadExecutor.class}
)
public class ConcurrencyConfig {}

// Custom qualifier for injection
@Qualifier
@Retention(RUNTIME)
@Target({METHOD, FIELD, PARAMETER, TYPE})
public @interface VirtualThreadExecutor {}

// Usage: inject and submit tasks
@Inject @VirtualThreadExecutor
private ManagedExecutorService managedExecutorService;

// Publisher runs on virtual thread - no platform thread consumed
publisherFuture = managedExecutorService.submit(() -> {
    while (running) {
        publishTrade(); publishQuote(); publishMarketDepth();
        LockSupport.parkNanos(5_000);
    }
});

All background tasks (publisher, subscriber polling, memory pressure generator, stats reporting) run on virtual threads. A single @ManagedExecutorDefinition replaces all thread pool configuration.

Luqman: Java 21 virtual threads through Jakarta Concurrency 3.1. This is huge for our use case - we need multiple background tasks that mostly block or park. Platform threads would be wasted.

The memory pressure generator spawns 4 parallel virtual threads per iteration. With platform threads, you'd need a thread pool. With virtual threads, each one is just a few hundred bytes on the heap.

GC Stress Testing

12 adversarial workloads targeting G1 weaknesses

Simon: This is the most important section. We designed 12 specific workloads across two categories: 5 memory scenarios that target G1 architectural weaknesses, and 7 CPU-intensive workloads that stress the GC under realistic compute pressure.

Why Scenario-Based Testing?

Generic Benchmarks Miss Real Behavior

Generic Benchmarks

  • Uniform allocation patterns
  • Don't model cross-generational refs
  • Miss promotion storms
  • Don't test fragmentation
  • Results don't match production

Targeted Scenarios

  • Each scenario targets one G1 weakness
  • Model realistic object lifetime patterns
  • Control allocation rate and live set
  • Reproduce deterministically
  • Expose real production behavior

Simon: Most GC benchmarks just allocate byte arrays in a loop. That tests allocation throughput but misses the nuances. Real applications have cross-generational references, promotion storms, fragmentation patterns.

    @Inject private Instance<Workload> workloads;

    private final ConcurrentLinkedDeque<byte[]> promotableObjects;

        }
    }
}

LONG_HORIZON_POSITION_BOOK: Remembered Set Stress

The Killer Scenario for G1


// Old-generation holder object (~1MB each, will be promoted by GC)
private static class RefHolder {
    volatile Object youngRef;  // Updated frequently
    final byte[] padding;      // ~1MB ensures old gen residence
    RefHolder(int size) {
        this.padding = new byte[size];
        ThreadLocalRandom.current().nextBytes(padding);
    }
}

// Create young objects and update old-to-young references
// Every write triggers G1's post-write barrier:
//   1. Marks card table entry as dirty
//   2. Adds to remembered set for later scanning
private void createCrossGenRefsMultiThreaded(int bytes, int threads) {
    RefHolder[] holders = crossRefHolders.toArray(new RefHolder[0]);
    for (int t = 0; t < threads; t++) {
        CompletableFuture.runAsync(() -> {
            while (remaining > 0) {
                byte[] youngObj = new byte[randomSize];
                holders[randomIdx].youngRef = youngObj; // write barrier!
                remaining -= size;
            }
        }, executorService); // virtual thread
    }
}

G1: Every youngRef write triggers write barrier + remembered set update. Overhead grows with cross-refs. Remembered set scanned during STW pauses.

C4: Uses a filtered write barrier (SVB) for card marks, but scans them concurrently. No STW pause for remembered set scanning.

Simon: This is the most interesting scenario. We create ~800MB of RefHolder objects that live in old generation. Each has a volatile reference field. Then 4 virtual threads continuously allocate new young objects and update random holders to point to them.

Every single write to youngRef triggers G1's post-write barrier. The barrier marks a card table entry dirty and potentially updates the remembered set. When young GC fires, G1 must scan all these remembered set entries to find live young objects during a stop-the-world pause. With thousands of old-to-young references, this becomes expensive.

C4 also uses card marks and a write barrier for old-to-young references. The difference is that C4 scans card marks concurrently - the young generation collector uses an interlock mechanism that briefly halts the old generation collector for page-granular synchronization, but the application threads never stop.

@ApplicationScoped
public class GCPauseMonitor implements NotificationListener {

    private final ConcurrentLinkedDeque<Long> pauseHistory;
    private final AtomicLong violationsOver10ms = new AtomicLong(0);
    private final AtomicLong violationsOver50ms = new AtomicLong(0);
    private final AtomicLong violationsOver100ms = new AtomicLong(0);

    @PostConstruct
    public void init() {
        for (GarbageCollectorMXBean gcBean :
                ManagementFactory.getGarbageCollectorMXBeans()) {
            if (gcBean instanceof NotificationEmitter emitter) {
                emitter.addNotificationListener(this, null, null);
            }
        }
    }

    @Override
    public void handleNotification(Notification n, Object handback) {
        // Filter out C4's "GPGC" bean (reports concurrent cycle, not pause)
        if ("GPGC".equals(gcName)) return;

        long pauseMs = gcInfo.getDuration();
        recordPause(pauseMs, gcName, gcAction);

        // Broadcast SLA violation to WebSocket clients in real time
        if (pauseMs > 10 && broadcaster != null) {
            broadcaster.broadcast(SLAViolationEvent.create(pauseMs, threshold));
        }
    }
}

Simon: GCPauseMonitor uses JMX GarbageCollectorMXBean notifications. Every GC event fires a notification with the pause duration. We track p50/p95/p99/p999 and broadcast violations to the browser in real time.

Important: we filter out C4's GPGC bean. It reports concurrent cycle times, not pause times. Including it would give misleading results.

    }

Conclusion

Key takeaways and lessons learned

Simon: Let's wrap up with the key takeaways and practical lessons from building this system.

Key Takeaways

  1. G1's stop-the-world pauses are architectural - no tuning eliminates them
  2. C4 collects concurrently - sub-millisecond safepoints at phase changes
  3. G1 pause time scales with live set - larger heaps = longer pauses
  4. C4 pause time is constant - independent of heap size or allocation rate
  5. Remembered sets add hidden overhead - cross-gen refs trigger write barriers on every pointer update
  6. Scenario-based testing exposes real behavior - generic benchmarks miss critical patterns
  7. Jakarta EE is a valid platform for low-latency trading - with the right runtime
  8. The application code stays simple - GC choice handles complexity without code changes

Simon: Eight takeaways. The first five are about GC. The last three are about methodology and platform choice. You don't need to rewrite your application to get near-pauseless behavior. You just need the right runtime.

Luqman: And Jakarta EE with Payara Micro gives you all the enterprise features you need - clustering, WebSocket, REST, configuration management - without sacrificing the performance that C4 provides.

Lessons Learned

What Worked

  • SBE flyweight pattern eliminates allocation on the hot path
  • Aeron IPC provides true zero-copy transport
  • C4 requires zero tuning for consistent pauses
  • Scenario-based testing reveals behavior that generic benchmarks miss
  • Virtual threads simplify concurrency for background tasks
  • Hazelcast clustering embedded in Payara removes infrastructure complexity

Watch Out For

  • C4's JMX bean reports as "GPGC", not "C4" - must filter this correctly
  • WebSocket JSON conversion adds measurable latency to the pipeline
  • 1-in-50 message sampling needed for UI stability under load
  • Docker shared memory sizing (tmpfs) for Aeron IPC requires attention
  • DIRECT mode's String.format is intentionally wasteful - don't use it as a performance reference

The biggest insight: The application code is identical between C4 and G1 deployments. The only difference is the JVM. The GC choice is a runtime decision, not an architectural one.

Luqman: On the practical side: we learned to filter GPGC from JMX notifications early on. The first version of GCPauseMonitor was reporting concurrent cycle times as pauses, which made C4 look worse than it is.

The 1-in-50 sampling rate was also a practical discovery. Without it, the WebSocket flood from 50K+ messages/sec crashes the browser.
