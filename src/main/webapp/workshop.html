When you open a JFR recording and see a GC pause, you are seeing a pause that interrupted a CDI bean method executing on a container-managed virtual thread. The Jakarta EE programming model is the constant; the JVM runtime is the variable.

1.0 Architecture Walkthrough

Before we touch JFR, let's walk through the source. Understanding the architecture is necessary context for the recordings you will read. Every component you see in the pipeline is a CDI bean in this project.

Virtual thread executor

The entire application uses a single Jakarta Concurrency 3.0 definition to create virtual threads:

java 
@ApplicationScoped
@ManagedExecutorDefinition(
    name = "java:module/concurrent/VirtualThreadExecutor",
    virtual = true,
    qualifiers = {VirtualThreadExecutor.class}
)
public class ConcurrencyConfig {}

Any bean that needs concurrent work injects @VirtualThreadExecutor ManagedExecutorService. The container creates the virtual thread factory; the application never touches Thread.newVirtualThreadPerTaskExecutor() directly. Five beans consume this executor: the Aeron subscriber, the market data publisher, the bar aggregator, the memory pressure service, and every workload implementation.

CDI lifecycle: startup and shutdown

The Aeron publisher and subscriber start when the CDI container initialises. They observe the @Initialized(ApplicationScoped.class) event:

java 
@ApplicationScoped
public class AeronSubscriberBean {

    void onStartup(@Observes @Initialized(ApplicationScoped.class) Object event) {
        mediaDriver = MediaDriver.launchEmbedded(new MediaDriver.Context()
            .threadingMode(ThreadingMode.SHARED)
            .sharedIdleStrategy(new BackoffIdleStrategy()));
        aeron = Aeron.connect(new Aeron.Context()
            .aeronDirectoryName(mediaDriver.aeronDirectoryName()));
        subscription = aeron.addSubscription(CHANNEL, STREAM_ID);
        executor.submit(this::pollLoop);
    }

    @PreDestroy
    void shutdown() { /* close Aeron, media driver */ }
}

This is the standard Jakarta EE pattern: observe a lifecycle event, start the resource, clean up on @PreDestroy. The Aeron media driver, the subscription, and the polling thread all live inside the container lifecycle.

WebSocket fan-out with Hazelcast

Four @ServerEndpoint classes push data to browser clients. The MarketDataBroadcaster is the bridge between the Aeron pipeline and the WebSocket sessions:

java 
@ApplicationScoped
public class MarketDataBroadcaster {

    @Inject HazelcastInstance hazelcast;

    private final Set<Session> sessions = ConcurrentHashMap.newKeySet();
    private ITopic<String> clusterTopic;

    @PostConstruct
    void init() {
        clusterTopic = hazelcast.getTopic("market-data-broadcast");
        clusterTopic.addMessageListener(msg ->
            broadcastToLocalSessions(msg.getMessageObject()));
    }

    void broadcast(String json) {
        clusterTopic.publish(json);
    }

    void broadcastToLocalSessions(String json) {
        sessions.forEach(session -> session.getAsyncRemote()
            .sendText(json));
    }
}

Each Payara Micro instance publishes to the Hazelcast ITopic. Every instance subscribes to the same topic and pushes to its own local WebSocket sessions. Clients connected to any node see the same data. This is how Jakarta EE clustering works with Payara Micro: the application code does not know about the cluster; the broadcaster just publishes to a topic.

JFR recording over REST

The JfrRecordingResource wraps the jdk.jfr programmatic API behind JAX-RS endpoints. You start a recording with POST /api/jfr/recording/start, list files with GET /api/jfr/files, and download .jfr files with GET /api/jfr/download/{name}. No jcmd, no SSH into the container, no docker exec. This pattern works in any Jakarta EE application on any JVM.

2.1 GC Events: What to Read First

JFR records dozens of GC event types. For pause analysis, three matter most:

EventWhat It Tells You
jdk.GarbageCollectionWall-clock pause time, cause, sum of phases. The headline.
jdk.GCPhasePausePer-phase pause breakdown (mark, evacuate, ref-processing). Where the time actually went.
jdk.GCPhaseParallel / jdk.GCPhaseConcurrentSubphase work, useful for distinguishing root scanning from object copy.

For G1 specifically: jdk.G1HeapSummary, jdk.G1HeapRegionInformation, jdk.EvacuationInformation, jdk.EvacuationFailed, jdk.PromotionFailed.

2.2 Pause Time Distributions

Average pause time lies. Distributions tell the truth.

P50nothing to worry about
→
P99worth keeping an eye on
→
P99.9this is the one that pages you at 3 AM
→
Maxdrop everything, the SLA is on fire

A 5-second recording at 60K msg/sec produces roughly 100 young collections under steady allocation. P99 over that sample size is barely meaningful. Workshop recordings are 60 seconds long for that reason, and even then your statistical confidence is limited. In production, recordings should be hours long for stable percentiles.

2.3 Young versus Mixed versus Full

The Collector Name column tells you which GC algorithm ran. This workshop compares ZGC against G1. The broader landscape includes four main collectors:

CollectorSourceStrategyPause Behaviour
G1OpenJDK 9+Generational, mostly concurrent. Young collections are STW.Pauses scale with live set. Typical 5-50 ms.
ZGCOpenJDK 11+ (prod JDK 15+)Generational (since JDK 21), fully concurrent.Sub-millisecond regardless of heap size.
ShenandoahOpenJDK 12+Concurrent, brooks pointers.Similar to ZGC: sub-millisecond.
C4Azul Platform PrimeFully concurrent, no STW phases at all.Zero pauses, even during compaction.

In the Garbage Collections view, filter by Collector Name:

Collector NameWhat G1 Was DoingSeverity
G1New (Normal)Young-only collection.routine maintenance
G1MixedYoung plus some old regions.the bill is coming due
G1OldWhole-heap, stop-the-world.the application stopped breathing
G1ConcurrentMarkMark phases running with the application.not a pause, working in the background

Common Causes

CauseMeaningWorry Level
Allocation RateApp allocating fast enough to fill young gen.this is normal, the app is doing work
G1 Evacuation PauseG1 moving live objects out of young regions.expected, but watch the duration
High UsageHeap occupancy crossed a threshold. ZGC initiates concurrent cycle.ZGC handling it, no human needed
G1 Humongous AllocationObject larger than half a G1 region. Causes fragmentation.your heap is getting Swiss-cheesed
System.gc()Explicit GC request from application code.find who called this and remove it
Metadata GC ThresholdMetaspace filled up. Often dynamic class generation.check if a framework is generating classes in a loop

How to read G1 Humongous Allocation: G1 divides the heap into fixed-size regions (16 MB in this workshop). Any object larger than half a region (8 MB) is "humongous." G1 cannot move these during collection, so they cause fragmentation and force immediate old-gen allocation. If you see it frequently, the fix is either smaller allocations or larger G1 regions (-XX:G1HeapRegionSize).

2.4 The Four Pathologies

GC pauses fall into four categories, each with a distinct JFR signature. These four patterns let you diagnose any GC problem from a recording, regardless of the application.

PathologyWhat Goes WrongAnalogy
Promotion StormObjects survive young-gen collections faster than the collector can promote them. Old gen fills rapidly.A conveyor belt dumping packages into a warehouse faster than the forklifts can shelve them.
FragmentationMany short-lived objects of different sizes leave the heap pitted with small free gaps. No single gap is large enough for a big allocation.A parking lot where every space has a motorcycle in it; no room for a delivery truck even though half the lot is "empty."
Cross-generational ReferencesOld objects hold many references to young objects. The collector must scan these during every young-gen collection, adding to pause time.A filing cabinet full of sticky notes pointing at documents on your desk. Every time you clear your desk, you have to check every sticky note.
Evacuation FailureThe collector tries to move objects out of a region but there is nowhere to put them. The entire heap is too full.A removals truck shows up but every storage unit in the city is already rented.

Triage Decision Tree

Start at the top. If the answer is yes, stop: you found the pathology. If no, move down.

1
Does pause time grow as old gen fills up?
Promotion Storm Objects surviving faster than the collector can promote them. Your heap is a conveyor belt with no off-ramp.
2
Lots of small, fragmented free regions?
Fragmentation Swiss cheese. Plenty of total free space, but no single gap big enough to use.
3
Is RememberedSet update time (scanning old-to-young pointers) eating your pause budget?
Cross-Gen Refs Old objects pointing at young objects. Every young GC follows thousands of sticky notes.
4
Do you see EvacuationFailed events?
Evacuation Failure Every storage unit in the city is already rented. The heap is full.

See analysis-checklist.md for the full triage tree with telltale JFR events per pathology.

2.6 GC Glossary

The terms above come up in every JFR recording. Here is what they mean.

TermPlain English
Young generationWhere new objects are allocated. Collected frequently. Most objects die here.
Old generationWhere objects that survived multiple young-gen collections live. Collected less often, but more expensive when it happens.
PromotionAn object surviving long enough to be moved from young gen to old gen.
Mixed collectionG1 collecting young regions plus some old regions in the same pause. More expensive than young-only.
Remembered setA per-region data structure tracking which old objects hold references to young objects. G1 must scan these during every young-gen collection. More cross-generational references = longer pause.
Write barrierCode injected by the JVM on every reference field write. Updates card tables and remembered sets. Adds a few nanoseconds to every pointer assignment your application makes.
EvacuationMoving live objects out of a region so the region can be reclaimed. The core operation of a copying collector.
PLABPromotion Local Allocation Buffer. Each GC thread gets a private buffer for promoted objects. Faster than shared allocation, but can waste space if the buffer is too big.
CompactionMoving live objects together to eliminate gaps. Necessary when fragmentation prevents allocation. Always requires a stop-the-world pause in G1.
Stop-the-world (STW)All application threads halt while the GC works. No progress is made. The metric you are trying to minimise.

3.1 The Shape of a Custom Event

A custom event is a public class extends jdk.jfr.Event annotated with @Name, @Label, @Category, and optionally @StackTrace(false) for hot paths.

java 
@Name("trade.published")
@Label("Trade Published")
@StackTrace(false)
public static class TradePublished extends Event {
    public String symbol;
    public long price;
    public int quantity;
    public String side;
}

Emit it from the publisher:

java 
TradePublished tradeEvent = new TradePublished();
if (tradeEvent.isEnabled()) {
    tradeEvent.symbol = symbol;
    tradeEvent.price = price;
    tradeEvent.quantity = qty;
    tradeEvent.side = side.name();
    tradeEvent.commit();
}

Critical detail: event.isEnabled() is the cost gate. When the event is disabled, isEnabled() returns false and the entire body is skipped. The JIT can sometimes eliminate the bare new TradePublished() allocation, but it cannot eliminate any computation you do to compute the field values (string concatenation, lookups, formatting). The isEnabled() gate guarantees field-population work runs only when JFR is recording the type.

@StackTrace(false) disables stack trace capture per emission. Stack traces are the most expensive part of a JFR event; for events that fire millions of times per second, leave them off.

3.2 Why Jakarta EE Apps Need Custom Events

In a Jakarta EE application, the container manages thread pools, connection pools, bean lifecycles, and the request/response cycle. Standard JFR events tell you what the JVM did: a GC pause here, a JIT compilation there. They do not tell you which business operation was running when the pause hit.

Consider this application. The MarketDataPublisher is an @ApplicationScoped bean running on a container-managed virtual thread. When a GC pause occurs, the JFR recording shows the pause. But without the trade.published event, you cannot tell whether the pause delayed 10 trades or 10,000. The domain event bridges the gap between runtime behaviour and business impact.

The same principle applies to any Jakarta EE application:

Jakarta EE BoundaryWhat a Domain Event Would Show
JAX-RS @POST handlerRequest latency including any GC pauses that occurred during deserialisation, validation, or persistence.
CDI @Observes async eventWhether the observer was delayed by a GC pause between the event fire and the observer invocation.
WebSocket @OnOpen / session broadcastHow many WebSocket messages were queued during a pause. Whether backpressure activated.
@ManagedExecutorDefinition taskWhether the virtual thread was unmounted during a GC pause, or pinned to its carrier.
@PostConstruct initialisationHow long startup took and where the time went. Relevant for cold-start latency in serverless-like deployments.

Rule of thumb: If a code path matters to your SLA, it needs a custom JFR event. GC events tell you the JVM paused. Domain events tell you what the pause cost in business terms.

3.3 Where to Emit From

  1. One event per logical operation, not per method call. Don't decorate every function; pick the boundary where the operation succeeded or failed.
  2. Numeric fields are cheap; String fields are not. Strings get interned in the JFR string pool, but the interning lookup is hot-path overhead. Use enums-as-ints where possible.
  3. Begin/commit pairs measure duration. Use event.begin() and event.commit() to capture elapsed time automatically; JFR records the start, end, and thread.

3.4 Correlating with GC Events

In JMC, the Event Browser lets you overlay timelines. To see whether GC pauses cause SBE encoding stalls:

  1. Find sbe.encode under Custom events.
  2. Find jdk.GCPhasePause under GC events.
  3. Drag both onto the same time axis.
GC pause: [---50ms---] SBE encode: ............ . . . . ^ ^ stalls catches up

If your SBE encode count drops to zero during the pause window, the publisher virtual thread is paused. If it does not drop, you have a virtual-thread carrier pinning problem.

5.1 Pattern Matching in Jakarta EE Applications

The four pathologies are not specific to trading systems. In a Jakarta EE application, the same pathologies show up in predictable places. The CDI bean model, the container-managed lifecycle, and the standard API patterns create characteristic allocation profiles that map directly to the four signatures you learned in Module 2.

PathologyJakarta EE Pattern That Causes ItJFR Signature
Promotion StormAn @ApplicationScoped bean with a growing cache (e.g., ConcurrentHashMap accumulating session data, or a Map<String, Price> that never evicts). Objects survive young-gen collections because the cache holds them, and old gen fills monotonically.jdk.PromoteObjectOutsidePLAB count climbing. Old gen growing. Mixed collections lengthen.
FragmentationCDI proxy objects, interceptor chains, and @JsonbTransient annotated DTOs create many small objects of different sizes per request. Long-running Payara Micro instances accumulate distinct object-size distributions over time.jdk.ObjectAllocationSample dominated by small objects. Object Copy phase dominates pause time.
Cross-gen RefsAn @ApplicationScoped broadcaster bean holding Set<Session> references. The bean is old gen; the sessions (and their buffers) are young gen. Every young-gen collection must scan the session set. The same pattern appears with any singleton that holds request-scoped objects.Update RS or Scan RS dominates pause time. ExecutionSample stacks in G1BarrierSet.
Evacuation FailureConnection pool or thread pool sized too large for the heap. Or ManagedExecutorService task queues filling faster than they drain during a burst. The heap has nowhere to evacuate live objects to.jdk.EvacuationFailed events. jdk.PromotionFailed events. Full GC triggers.

Why this matters for Jakarta EE developers: The container abstracts away thread management, pooling, and lifecycle. That abstraction is valuable, but it also means you cannot see what the container is doing to the heap. JFR is the tool that makes the container's allocation behaviour visible. The four signatures above appear in any Jakarta EE application under load; the only difference is which bean and which API boundary triggers them.

The take-home reference is exercises/module-5-apply-to-your-app/gc-pathology-catalog.md, which restates the four patterns with their JFR signatures, plain-language root causes, and a fix-order list per pattern.

5.2 Allocation versus Collector Choice

The hardest call in performance work is: do I reduce allocation, or do I change collector?

1
Allocation rate > 500 MB/sec?
Reduce allocation first Flyweight patterns, off-heap buffers, primitive arrays. Cheaper than changing JVM.
2
Heap > 8 GB?
Consider concurrent collector ZGC or Shenandoah. G1's pauses scale with live set beyond this point.
3
Pause-sensitive, but P99 still acceptable?
Tune G1 MaxGCPauseMillis, InitiatingHeapOccupancyPercent. Squeezing the last mile.
4
None of the above helped?
Move to concurrent collector You have optimised the hot paths and the residual GC cost is still too high. Change the JVM, not the code.

Reducing allocation is almost always cheaper in production than changing JVM. The exception is when you have already optimised the hot paths (zero-copy, flyweight, primitive arrays) and the residual GC cost is still material.

5.3 Production-Safe JFR

Three rules for always-on JFR in production:

  1. Use the default profile, not workshop. -XX:StartFlightRecording=settings=default is the 1%-overhead setting. The workshop profile is 1-2%.
  2. Cap the size. maxsize=1g,maxage=24h keeps recordings circular without unbounded disk growth.
  3. Disable stack traces on hot events. @StackTrace(false) on every custom event you emit more than 1000 times per second.

See exercises/module-5-apply-to-your-app/production-jfr-flags.md for reference flags.

5.4 Event Templates

Three reusable event templates for your own applications, in exercises/module-5-apply-to-your-app/event-templates/:

TemplateWhen to Use It
LatencyEventWrap any function whose tail latency matters; uses begin()/commit() for automatic duration.
ThrottleEventEmit when a circuit breaker opens, a rate limit is hit, or backpressure activates.
ResourceEventEmit when a finite resource (connection pool, file handle, cache slot) is reserved or released.

Copy these into your own project, rename them, and start instrumenting.

Takeaways

  1. JFR is the diagnostic of record for production Jakarta EE applications. Ship every container with always-on JFR.
  2. The four GC pathologies have signatures you can recognise in any application on any JVM runtime.
  3. event.isEnabled() and @StackTrace(false) are the two rules for production-grade custom JFR events.
  4. Stress-test before shipping. JFR tells you what happened; pre-production stress tells you whether it will happen in prod.
  5. The runtime is a production decision with measurable consequences. The recording, not the brand, decides. Today you read OpenJDK runtimes. The same skill applies to any JVM, including those that sit above the ceiling you measured.
